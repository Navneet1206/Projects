# High-Availability Cluster Root Cause Analysis (RCA)

This project contains a detailed Root Cause Analysis (RCA) and post-mortem report for a critical production incident that occurred in a 2-node High-Availability (HA) cluster running SUSE Linux Enterprise Server (SLES) for SAP Applications.

The repository includes the full engineering investigation report alongside the actual systems diagnostic archives (`supportconfig` bundles) that were analyzed to diagnose the failure.

## Repository Contents

*   **[RCA.md](RCA.md)**: The comprehensive Incident Investigation and Root Cause Analysis report detailing the problem statement, chronologically structured event timeline, technical deep-dive findings, business impact, and remediations.
*   **`scc_iprslesdqap_260401_1128.txz`**: Diagnostic system archive generated by SUSE `supportconfig` on the primary active cluster node (`iprslesdqap`).
*   **`scc_iprdqapd_260401_1129.txz`**: Diagnostic system archive generated on the secondary cluster node (`iprdqapd`).
*   **`scc_iprappprd_260401_1114.txz`**: Diagnostic system archive generated on the SAP application environment controller node (`iprappprd`).

## Scenario & Diagnostic Overview

The active cluster node (`iprslesdqap`) entered a reboot loop, restarting five times consecutively within a 79-minute window. The incident was initiated during network maintenance on the secondary node (`iprdqapd`), where a restart of the network daemon disrupted cluster heartbeats and led to an unsuccessful STONITH fencing command, resulting in automatic hardware watchdog self-fencing.

### SRE & Systems Administration Concepts Demonstrated

1.  **High-Availability Clustering**: Configuration and troubleshooting of Pacemaker (resource manager) and Corosync (membership/heartbeat daemon) in a multi-node environment.
2.  **Fencing Mechanisms (STONITH/SBD)**: Storage-Based Death (SBD) fencing using shared block storage devices, and debugging watchdog-driven system resets.
3.  **Linux Network Stack Troubleshooting**: Analyzing `wicked` daemon behavior, bridge configurations, ARP tables, routing paths, and interface status.
4.  **SLES Supportconfig Analysis**: Inspecting log files (such as `/var/log/messages`, `/var/log/wtmp`), daemon statuses (`pacemaker.service`), and network configurations extracted from supportconfig archives.

## Findings Summary

*   **Primary Cause**: A restart of the `wicked` service on the secondary node resulted in local routing table corruption and network isolation, cutting off cluster heartbeat traffic.
*   **Secondary Cause**: Fencing command from the DC node failed due to the network isolation.
*   **Contributory Vulnerability**: Mismatched SBD watchdog timeouts (5s in software vs 60s in SBD disk header) and an aggressively low Corosync token timeout of 5s, which triggered rapid, consecutive hardware watchdog reboots.
